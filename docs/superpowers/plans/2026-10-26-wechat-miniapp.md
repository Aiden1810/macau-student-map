## 1. 目标和推荐决定

为澳门学生提供一个能在微信中直接使用的城觅入口，逐步完成：

**浏览／搜索地点 → 查看真实资料 → AI 辅助比较 → 打开地图导航；登录后保存收藏。**

推荐采用 **Taro + React + TypeScript 小程序客户端，保留 Next.js 网站、网页管理后台和 Supabase 数据**。这是本次建议，尚未当作用户已经选定的技术决定。

网站和小程序是两个界面，背后使用同一套业务数据与服务。先打通一条真实流程，再扩充功能。现阶段不增加 Python 后端，不整体重构数据库，也不先引入复杂的 monorepo 工具。

## 2. 为什么这样选

| 路线 | 优点 | 代价与本项目适配情况 |
| --- | --- | --- |
| Taro + React + TypeScript（推荐） | 延续现有 React、TypeScript，便于理解已有业务逻辑 | 页面、样式、路由和平台能力仍需适配；Taro 不是 Next.js 一键转换工具 |
| 原生微信小程序 + TypeScript | 直接学习小程序页面与组件机制，平台能力接入直接 | 需要补学 WXML、WXSS 和另一套页面组织方式，网页组件复用更少 |
| uni-app + Vue | 适合已有 Vue 经验或明确需要其生态的项目 | 本项目已有 React，当前额外转向 Vue 的收益不足 |

个人主体不采用 web-view 包装现有网站：2026-10-26 读取的微信官方组件文档仍明确写明，个人类型小程序暂不支持该组件。

## 3. 当前项目核查结论

以下为本地源码核查，不代表重新检查过云端配置或线上健康状况。

| 现状 | 对实施的影响 |
| --- | --- |
| Next.js 15、React 19、TypeScript；Node.js 要求为 24.x | 网站继续保留；小程序依赖按 Taro 官方模板兼容组合独立锁定，不强行与网站 React 同版 |
| 已有 `/api/shops`、`/api/places`、`/api/places/[id]` | 能复用部分数据读取，但接口还不是统一的小程序数据契约 |
| 首页通过 `mergeLegacyAndCanonicalPlaces` 合并旧 `shops` 与新 `places` | 不能只接 `/api/places` 就认为拿到了网站全部地点；详情、收藏和评价的 ID 关系要一起核对 |
| `lib/auth/require-user.ts` 校验 Supabase access token | 微信 OpenID 或任意自签 token 不会自动被现有接口认可 |
| `lib/hooks/useFavorites.ts` 直接使用浏览器存储和 Supabase，收藏读取 `shop_id` | 需要小程序存储适配和收藏 API；不可把两类地点 ID 随意写入旧外键 |
| AI 聊天识别在服务端，高德 POI、路线比较主要在浏览器执行 | 可以复用 AI 识别及推荐规则，地图搜索和路线服务需要独立适配 |
| 根 `tsconfig.json` 包含全部 `**/*.ts`、`**/*.tsx`；ESLint 使用 Next.js 规则 | 新增 `miniapp/` 时必须隔离网站类型检查和 lint 范围，避免互相影响 |

主要参考：`app/[locale]/page.tsx`、`lib/data/canonical-places.ts`、`lib/data/shop-detail.ts`、`lib/api/places-detail-route.ts`、`lib/hooks/useFavorites.ts`、`lib/api/place-chat-route.ts`、`lib/amap/route-comparison.ts`。

## 4. 首版范围

分成三个可验收版本，避免“基础页面做完”被误认为整个小程序已完成。

| 版本 | 功能 | 验收结果 |
| --- | --- | --- |
| A：基础 MVP | 真实地点列表、名称搜索、分类／区域筛选、详情、图片、地图标记、打开地点地图 | 手机微信里能找店、看资料、打开地图；无定位也能完成浏览 |
| B：核心演示版 | AI 对话、预算／人数比较、地点与起点确认；逐项验证 POI、真实路线比较 | 能完成原项目的 AI 找店与比较流程；路线不可用时明确反馈 |
| C：账号内测版 | 微信登录、会话恢复、退出、云端收藏、“我的”、地点分享 | 收藏归属正确，账号之间隔离；分享能打开对应地点 |

账号接入技术验证在阶段 0 就开始，完整账号页面稍后实现，不把架构难题留到最后。若验证发现身份接入影响接口设计，先解决再继续用户写入功能。

首轮暂缓：投稿、评价发布、图片上传、账号跨端绑定、聊天云同步、复杂推送和付费。已有公开评价可按数据契约展示。管理员继续使用网页后台。

AI 是核心演示范围；如账号类目或审核条件暂不允许公开开放 AI，保留基础版本，明确受限原因，不把受限功能描述为已经上线。

首版建议先完成简体中文；字段、编码保留后续繁体和英文扩展空间，不直接搬用 Next.js 的语言路由。

## 5. 结构与职责

```text
CityU_Food/
├─ app/                         现有网站、后台和服务端 API
│  └─ api/miniapp/              按需新增的小程序接口适配层（拟建）
├─ components/                  现有网页组件
├─ lib/                         现有业务、数据与校验逻辑
├─ supabase/                    现有数据库迁移与权限测试
├─ docs/                        设计、步骤、验收记录
└─ miniapp/                     独立小程序客户端（拟建）
   ├─ package.json              独立命令与依赖
   ├─ package-lock.json         锁定小程序依赖
   ├─ config/                   Taro 编译与环境配置
   ├─ project.config.json       微信开发者工具项目配置
   └─ src/
      ├─ app.tsx
      ├─ app.config.ts
      ├─ pages/                 discover、detail、assistant、profile
      ├─ components/            小程序卡片、筛选等组件
      ├─ services/              request、places、auth、favorites、assistant
      ├─ types/                 接口数据类型
      └─ utils/                 storage、location 等平台适配
```

以上为建议结构，实际文件以创建时的 Taro 模板为准。首期按“发现、AI 助手、我的”组织主要入口，地点详情作为子页面；A 版本先提供发现和详情。

数据流：小程序 → 共用 Next.js API → Supabase／AI／按需接入的地图服务。网页后台仍负责资料维护与审核。

小程序先通过业务 API 访问数据；图片不强制全部代理，但需要逐一验证实际图片域名、访问方式和网络。数据库服务端密钥、微信 AppSecret、session_key 和 AI Key 不进入小程序包。

## 6. 逐步执行任务

### 阶段 0：账号准备与三个技术验证

**目的：尽早确认能否按这条路线在真实微信环境运行。**

1. 注册前确认个人主体可选服务类目，核对本产品的地点信息、AI 和用户内容是否适用；注册账号并取得 AppID。
2. 安装 Windows 微信开发者工具，添加开发者／体验成员；AppSecret 只在服务端配置，不发到聊天或仓库。
3. 验证网络：真实手机读取少量公开地点与图片，分别检查澳门本地 Wi-Fi、移动网络；若面向珠海用户，再检查内地网络。
4. 核对接口 HTTPS、合法域名、证书与备案条件。已有 Vercel 部署不直接等同于可配置的小程序服务器域名。
5. 评估共用后端的实际部署：先验证现有部署配合合规域名的可行性；如不满足，再比较合规的服务器部署或微信云托管。保留业务代码，依据网络与平台条件选择，不预先购买或迁移服务。
6. 验证地图：选定澳门、氹仔、横琴／珠海的真实地点，核对地图标记、坐标来源、定位权限与打开地图行为。定位不可用时保留区域筛选、学校起点和手动选择。
7. 验证微信登录如何映射现有 Supabase 用户，以及如何获得现有权限层认可的会话。先在隔离环境验证，不以正式用户数据试验。

**交付：**账号／类目能力表、真实网络记录、地图样本记录、身份接入决定及涉及的数据库改动清单。阶段 0 的小程序验证工程在正式启动开发后创建，本轮没有创建。

**通过条件：**有可用的真机数据通路；已确定定位不可用的替代交互；账号权限接入有可验证方案。注册和审核等待单独记录，不纳入固定开发天数。

### 阶段 1：建立独立小程序工程并接通只读数据

**涉及：**新增 `miniapp/`；按需修改根 `tsconfig.json`、`eslint.config.mjs`、`.gitignore`；新增小程序启动说明。

1. 使用兼容的 Taro + React + TypeScript 模板，独立安装并锁定依赖，记录 Node、Taro、React 与基础库版本。
2. 隔离网站和小程序的类型检查、lint 及构建产物；网站现有运行命令继续可用。
3. 实现统一请求封装：绝对 API 地址、超时、HTTP／业务错误、重试入口、请求标识；不直接复制浏览器 `fetch` 封装。
4. 先完成列表和详情纵向流程，加载真实图片，提供 loading、空结果和失败状态。

**通过条件：**开发工具和手机微信都能打开真实列表及详情；关闭调试、关闭跳过域名检查后验证可用；网站原有检查通过。

### 阶段 2：统一地点接口并完成基础 MVP

**涉及：**按需新增 `app/api/miniapp/` 与 `lib/api/` 适配；复用 `lib/data/`、`lib/mappers/`、`lib/services/search-places.ts` 和现有筛选规则；新增针对性接口测试。

1. 定义稳定的地点响应：地点 ID、来源、名称、地址、图片、价格／币种、分类、坐标和公开状态。未知值显示未知，不填伪造数值。
2. 复用已有双源合并规则，在服务端处理兼容。保留 `source` 与原始 ID，不把拼接字符串强塞入 UUID 外键。
3. 建议新增列表／详情适配接口，路径可采用 `/api/miniapp/places` 与 `/api/miniapp/places/:source/:id`。这些是拟新增路径，当前不存在。
4. 列表明确每页上限、筛选、排序与分页语义；先复用现有搜索规则，不为小数据量引入独立搜索引擎。内存过滤是否足够依据数据量验证。
5. 完成搜索、分类／区域筛选、地图与列表联动、地点详情和打开地点地图。定位按用户操作触发，不是进入页面的必要条件。

**通过条件：**小程序和网站对同一公开地点的信息一致；双源数据不重复、不漏来源；草稿和下架地点不公开；翻页、筛选、无结果与失效地点行为正确。

### 阶段 3：迁移 AI 与地图比较

**涉及：**复用 `/api/assistant/chat` 和 `lib/assistant/` 的可移植规则；适配 `lib/amap/` 依赖的 POI 与路线能力；新增小程序聊天界面。

1. 保留“AI 解析需求，代码读取真实地点与计算结果”的逻辑。第一步先验证现有 JSON 聊天接口，不为迁移额外增加流式架构。
2. 小程序实现消息、起点／门店确认、新对话、请求取消和失败重试；不直接搬用网页浮窗、dialog 与 localStorage。
3. 地图 POI／路线按阶段 0 结果选择小程序兼容能力或服务端供应商接口，重新确认 Key 类型、授权范围与额度。Web JS Key 不直接视为通用 Key。
4. 路线时间来自实际地图结果，缺失时提示无结果；区分步行、公交、驾车，跨境路线不包含虚构过关时间。
5. 公开开放前提供共享限流、用户／会话额度与预算上限；现有进程内 IP 限流不足以单独承担多实例费用保护，校园共用 IP 也需考虑误伤。

**通过条件：**真实需求可以重复完成确认、比较、导航；追问保留正确上下文；取消后旧结果不覆盖新对话；服务异常和额度不足有明确反馈。

### 阶段 4：微信登录与云端收藏

**涉及：**拟新增微信认证与收藏接口、小程序账号界面；按验证结果修改 `lib/auth/`，必要时新增 Supabase migration（迁移）与权限测试。

1. `wx.login` 取得 code → 后端调用 `code2Session` → 按 AppID + OpenID 查找身份映射 → 建立业务会话。
2. 详细落实阶段 0 的身份方案：若能接入 Supabase 认可的用户会话，延续现有 RLS；若需要独立业务会话，必须另行设计服务端授权与数据库边界，不能声称现有 `auth.uid()` 会自动认可。
3. 定义有效期、刷新／重新登录、退出与凭证失效策略；保留游客浏览，收藏等操作再请求登录。
4. 云收藏接口从服务端认证结果确定 user_id，先确认新旧地点与收藏表的关系；同时验证账号切换时的本地缓存隔离。
5. 网站邮箱账号与微信账号不自动合并，跨端同步留待可验证的绑定流程。头像、昵称和手机号不是登录必需条件。

**通过条件：**两个真实测试账号无法读写彼此收藏；重新打开恢复有效登录；过期、退出、取消登录和切换账号正确；伪造 user_id／OpenID 不能越权。

### 阶段 5：小范围内测与发布准备

1. 邀请少量同学做任务测试，建议先覆盖 5～10 位体验成员；这是体验采样规模，不是容量承诺。
2. 覆盖 iOS／Android、澳门目标网络、弱网、定位拒绝、后台返回、重复点击、分享进入和接口超时。
3. 补齐当前主体适用的隐私政策、用户协议、账号数据管理及小程序备案／发布要求；具体材料以实际账号后台为准。
4. 核对图片、接口、定位与 AI 的声明和权限；通过功能开关控制未满足发布条件的能力。
5. 按实际目标并发验证关键 API 的耗时、失败率和费用，记录测试条件。新版客户端不会自动提升数据库容量。
6. 留存发布版本、检查结果和回退步骤，再提交审核；不承诺固定审核天数或必然通过。

**通过条件：**关闭所有开发调试放宽项后，目标手机／网络能完成已开放功能闭环；阻断问题已解决，运营与费用可观察。

## 7. 时间安排与当前下一步

建议按每周一个可演示里程碑组织，不按页面数量评价进度：

- 第一里程碑：账号条件清楚，真机通过正式域名读取真实地点与图片。
- 第二里程碑：基础 MVP 完成，搜索、详情、地图链路可用。
- 第三里程碑：AI 找店和比较可演示，地图能力与费用边界清楚。
- 第四里程碑：微信登录和云收藏完成，开始同学内测。

这是推进节奏，不是每个里程碑必定一周完成的工期承诺。由于账号尚未注册、域名发布条件和身份桥接未验证，当前不估算精确总工期；阶段 0 完成后，再依据你每周可投入的时间估算。

**正式开发的第一个任务包：账号／类目核对 + 独立工程基础配置 + 真机只读地点验证。**先做到“手机微信可以读取一条真实地点并正确打开详情”，再继续搜索和地图。

## 9. 官方核对资料与边界

2026-10-26 已直接读取以下微信官方页面：

- [网络与服务器域名](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)：常规请求需配置通讯域名，HTTPS／WSS、域名 ICP 备案等限制；使用微信云托管特定接口有不同接入方式。
- [登录流程](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)：code 由服务端交换身份，业务登录态仍需开发者建立。
- [web-view](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)：个人类型小程序暂不支持。
- [getLocation](https://developers.weixin.qq.com/miniprogram/dev/api/location/wx.getLocation.html)：定位接口涉及类目和开通要求；不能假定注册后自动可用。
