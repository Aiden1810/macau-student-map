### 1.1 最新首发范围与顺序（用户进一步明确）

“各端同步”按用户前台、管理员后台、投稿表单、手机/电脑布局、列表、详情和地图使用一致地点信息理解，不涉及新建原生 App。

1. **本轮接入最小导航入口**：保留站内“查看位置”，新增“用高德导航”，把已确认分店坐标交给高德；提供复制地址和网页版备用入口。

### 1.2 分类与地图一致性的最小设计

实施前代码核对结果（以下缺口已在本地实现中处理，未代表线上生效）：

- `lib/domain/taxonomy.ts`、`lib/tags/schema.ts`、`lib/search/filter-options.ts` 已有理发、桌游等标签，但当前目录没有独立酒吧和剧本杀标签。
- `components/MapPlaceholder.tsx` 中 `buildShopPinHtml` 不接收地点类别，选中和排名标记复用固定餐具图案；不仅要改某个选中图钉，还要覆盖普通、选中、悬停和筛选状态。
- 投稿和卡片仍有“人均消费”“必点”等餐饮用语，生活地点需要适合行业的表述。

实现原则：

- 维护一份分类/标签定义及图标映射，筛选、投稿、后台、卡片和地图共同消费；不在每个页面手写一份标签清单。
- 新标签既要能显示，也要能被提交、后端校验和保存，并在审核后的公开地点中正确读回。先核对数据库目录中是否已有对应标签，不随意编造 UUID；如需要数据库补充，单列授权事项。
- 图标优先由明确的具体类型决定，其次按主分类使用通用图标；多个类型命中时有固定优先级，不以 `tags[0]` 或店名猜测代替分类规则。
- 同一个地点 ID 对应同一分店和坐标；列表点“查看位置”后地图定位并选中该地点，点击地图也能打开对应卡片/详情。切换筛选时清理已经不在结果中的旧选择。
- 管理员审核或更新成功后，在当前页面刷新相关数据；另一端刷新/重新进入能读取相同已发布结果。首版不承诺跨设备毫秒级实时同步，也不以新增 Realtime 代替正确刷新。
- 非餐饮地点统一使用“消费参考”，明确如理发按次、桌游按小时、门票按人等实际计价方式。现有结构不能表达的单位先保留在已支持的说明中，不把每小时价格写成人均、不虚构字段。

联合验收至少覆盖：饭店、理发店、酒吧、桌游/剧本杀地点的“选择具体 POI → 投稿/后台录入 → 审核 → 前台筛选 → 查看位置 → 正确图标 → 详情 → 导航”，并单独核对只提供桌游或只提供剧本杀的地点不会被误标。另覆盖同名分店、标签顺序变化、无坐标和手机/电脑布局。自动测试可用本地假数据；线上不创建虚构公开地点。

2026-09-12 本地实施记录：

- 共用 `lib/domain/place-types.ts` 定义四类入口、主标签、展示名称和图标；投稿、后台、筛选、卡片、详情、审核队列和地图接入此定义。
- 地图普通、选中、悬停和筛选标记按类型展示：餐具、剪刀、酒杯、骰子、推理放大镜；桌游与剧本杀共用入口、单独筛选。
- 非餐饮价格使用“消费参考 MOP …/人次”，缺失时显示待补充；小时价、包场价不要填入该字段。
- 用户授权并已执行 migration：`20260912034831_launch_life_categories.sql`。仅补酒吧/剧本杀标签及别名、扩展旧 shops 分类 CHECK，保留原分类；应用代码通过本次发布提交上线。
- 投稿提交前检查数据库是否存在全部所选有效标签，缺失或目录读取失败时保留草稿并提示暂不可用，避免审核时静默丢失类型。
- 审核通过和合并前再次检查投稿标签仍然有效；目录异常或标签已停用时拒绝发布，避免 RPC 只写入部分标签。
- “各端同步”指同一分类契约、写入后刷新/重新进入读回一致；没有新增跨设备 Realtime 保证。
- 当前下一步：部署成功后进行用户联合验收；本地 pgTAP 待具备 Docker Desktop / Podman 后补跑。具体步骤见[四类地点验收说明](../../life-categories-acceptance.md)。

### 1.3 导航方案与难度

| 方案 | 相对难度 | 首版选择 |
| --- | --- | --- |
| 打开高德路线页面或尝试唤起高德 App | 较低，主要是坐标和浏览器兼容处理 | 推荐；无需自己实现路线算法，优先步行入口 |
| 在本站地图绘制步行/公交路线和预计时间 | 中等，要处理起点定位、路线服务、界面与失败反馈 | 后续按实际需求增加 |
| 在本站持续定位、语音播报和偏航重算 | 高，涉及持续定位与移动端体验 | 暂缓，交给导航 App |

官方依据：[URI 路径规划](https://lbs.amap.com/api/uri-api/guide/travel/route)、[JS API 2.0 路线规划](https://lbs.amap.com/api/javascript-api-v2/tutorails/car-dir)。URI 文档提供移动端唤起参数，也明确微信/QQ 内置浏览器可能无法唤起。地图已经显示不等于导航已经接通，也不等于澳门每种交通方式均已验证。

导航实施与验收重点：以分店坐标而非单纯店名作为目的地；核对坐标来源和坐标系，避免重复转换；无坐标不构造假路线；实际测试澳门步行目的地、iOS/Android、微信与普通浏览器、未安装高德或定位被拒绝的情况。高德之外的地图入口根据问卷反馈另行评估。

本轮本地实现采用共用 `PlaceNavigationActions` 组件，连接桌面店铺卡片、独立详情页及移动详情组件。链接默认步行，提供不唤起 App 的网页版链接；自动复制失败时显示可手动复制的地址。外部 App 唤起和澳门实际路线仍须真机验收，不以链接测试替代。

## 3. 保留的借鉴方向

| 优先级 | 借鉴点与截图依据 | 适合本项目的最小落地方式 | 验收重点 |
| --- | --- | --- | --- |
| 高 | 推荐理由、价格与特色内容放在一起（图 6） | 展示已有一句话推荐、推荐菜或服务项目、实际人均消费；优先回答学生预算与使用场景 | 有数据才显示；缺失不编造；价格有币种，不将不确定价格当作实时事实 |
| 高 | 导航、收藏等主要操作集中（图 6） | 改善手机详情页主要操作，提供复制地址和免费基础导航；复用既有入口与逻辑 | 目的地和分店正确；无坐标、复制失败有反馈；收藏先确认 canonical 兼容性 |
| 高 | 地点纠错入口（图 6） | 支持“已停业、位置不对、价格变化、优惠失效”，交给管理员核实 | 用户报告不直接改公开地点；报告状态可追踪；先检查能否复用既有修改建议流程 |
| 中 | 推荐者、日期和理由可见（图 1、6） | 先显示允许公开的投稿昵称、投稿日期；有真实核实记录时再显示核实日期 | 不泄露邮箱等资料；有头像或通过审核不等于实地核实；普通更新时间不能冒充核实时间 |
| 中 | 个人记录集中（图 4） | 在现有能力上完善“我的收藏、我的投稿、审核状态”入口 | 用户能看到自己的投稿状态；明确本地收藏与账号同步的实际能力 |

本轮保留的是上述方向，不承诺一次性全部实现。收藏、投稿和站内查看位置等既有能力继续复用；外部高德导航由本轮新增的共用组件提供。

暂缓或不采用：

- 地图密集大头像：图 3 已有明显遮挡；继续优先保证地点和店名清楚，推荐者放在选中地点卡片中。
- 大规模内容瀑布流、关注粉丝体系：内容供给和持续使用尚未验证，先考虑少量学生精选。
- VIP、基础导航收费、原生 App：不进入近期 MVP。
- 无依据的“推荐度 95%”：如未来展示推荐率，须同时说明人数和计算口径；样本少时直接展示人数。
- 一次性重构全部数据模型、AI 搜索、全澳门大规模覆盖：保留长期方向，按实际需要分步实施。
