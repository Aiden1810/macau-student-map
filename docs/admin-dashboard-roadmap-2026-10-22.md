# 后台运营与 API 用量看板需求记录

记录日期：2026-10-22。用户希望从平台负责人的角度逐步完善后台数据管理，特别关注注册增长和 AI 助手等 API 的调用消耗。沿用“先记录、暂不开发”的安排；本轮没有新增采集、建表、购买服务或部署。

## 看板需要回答的问题

| 看板 | 主要指标 | 帮助负责人判断什么 | 优先顺序 |
| --- | --- | --- | --- |
| 用户增长与使用 | 注册总数、近一天／七天新增注册、实际使用功能的登录账号数、回访情况 | 是否有人注册，注册后是否继续使用 | 第一阶段 |
| AI 与外部 API 用量 | 助手请求数、外部调用数、Token、成功率、超时、耗时、预计费用、额度和预算提醒 | 哪个功能消耗大，是否值得继续投入，是否出现异常调用 | 第一阶段 |
| 系统运行与资源 | 关键接口错误率、响应时间、慢请求、图片上传失败、数据库／图片存储／流量等资源用量 | 网站是否正常，用户是否遇到故障，是否接近套餐额度 | 第一阶段先做关键接口，资源汇总后续接入 |
| 搜索与使用效果 | 热门搜索、无结果搜索、店铺详情查看、收藏、导航点击、AI 推荐结果点击 | 用户需要什么店铺，是否找到了有用的信息 | 第二阶段，复用现有搜索分析 |
| 内容与审核效率 | 新增投稿、新发布店铺、新增评价、待处理反馈、审核处理时间、最久未处理事项 | 内容是否增长，管理工作是否积压 | 第二阶段，复用现有待办和审核流程 |
| 店铺资料健康 | 缺图片／地址／坐标、位置描述不完整、待处理纠错、长期未核实的资料 | 哪些店铺需要补充或核实 | 第二阶段，复用现有资料质量入口 |

已有访问趋势、设备与来源、热门／无结果搜索、资料质量和待办等基础功能。上述项目是延续和补充，不重复新建相同统计。

## AI／API 消耗的统计要求

### 分清统计对象

- 网站接口请求：用户请求了多少次助手、搜索或投稿接口，包含校验失败、限流等情况。
- 真正发出的外部调用：服务器或浏览器实际请求了多少次 DeepSeek、高德地图等外部服务。未发出外部请求、从缓存直接返回等情况分别标注。
- 用户的一次操作可能触发多个外部请求；若以后增加重试，也要区分用户操作、调用尝试和重试次数，不能重复算成新用户。
- AI、地图与其他接口分别展示；地图后续可按地点搜索、路线查询等功能拆分。

### AI 看板希望显示的内容

1. 指定时间范围内的助手请求数、模型调用数、成功／失败／超时／取消数量，以及限流拦截数量。
2. 使用助手的去重账号数；匿名使用单列，不能凭浏览器标识推断实际人数。
3. 输入 Token（发送给模型的文本计量单位）、输出 Token（模型回复的文本计量单位）及供应商提供的缓存用量。
4. 模型、供应商和功能入口的分类汇总，区分两个现有助手入口。
5. 平均响应时间及慢请求情况；后续可增加 P95（95% 请求的耗时不超过该数值）。
6. 当日／近七天／当月预计费用，以及每次成功使用的平均成本；显示币种、估算依据和价格生效日期，最终扣费以供应商账单为准。
7. 可配置的预算或额度提醒，例如达到预算的 80%、接近当日调用上限、失败率异常。阈值和通知方式留待实施时确定，不在本轮创建自动化提醒。

当前两个模型适配器位于 lib/assistant/model.ts 和 lib/assistant/chat-model.ts，均使用 AI SDK generateText 调用 DeepSeek，只提取 output，没有持久化 usage。当前 maxRetries=0；“重试次数”是未来可能需要的口径，不表示目前已经开启自动重试。

AI SDK 能提供模型返回的 Token 用量，但某些字段可能缺失。失败、超时或取消后没有取得用量时，记录“用量未知”，不能填 0 或宣称没有扣费。没有历史采集记录的明细不能凭空回补；是否能够补回供应商侧历史，需另查供应商日志、账单或导出能力。

## 数据来源与准确性

- 付费 API 的实际调用和 Token 消耗以服务端记录及供应商返回为依据；前端按钮点击只用于说明使用行为。
- 区分 HTTP 请求成功、外部服务调用成功、模型结果解析成功和用户得到可用结果，避免接口返回 200 就被当成完整服务成功。
- 注册、活跃登录账号、匿名浏览器、页面浏览量分别统计。活跃账号需先定义有效行为；回访或留存要先定义统计周期和用户集合。
- 搜索无结果率需明确分母；导航点击表示用户点击导航，不代表实际到店；收藏不代表交易。本项目当前不引入订单、成交额等不存在的业务指标。
- 审核效率基于真实提交／处理时间，区分已处理耗时与待处理等待时间；批准率明确是否包含合并、草稿和未处理记录。
- 使用统一的澳门时间和清楚的范围名称，近一天／近七天边界沿用注册增长需求，实施时确认。
- 排除或单列本地开发、预览、测试和已识别的自动化流量，避免测试调用混入正式运营统计。
- 费用估算、供应商账单、套餐已用额度分别标识，不根据访问人数直接推算账单。
- 统计采集失败应显示缺失或不完整，不能默认为零。采集本身应尽量不拖慢正常业务，并考虑日志保留周期和存储成本。

Vercel 的请求／函数／外部请求事件、Supabase 的资源使用页面可作为运行及资源数据来源。能否自动汇总到本项目后台，需另核实授权、套餐、接口和保留期；当前不承诺所有指标都能直接获取。Supabase 查询、Vercel 请求和 DeepSeek 调用的计量单位不同，分别核算。

## 权限与记录范围

- 看板仅限管理员读取，沿用现有管理员权限校验；敏感统计不进入公开接口和公共缓存。
- 用量日志优先保存时间、功能、模型、请求关联编号、状态、耗时、Token 和估算费用等必要元数据。
- 不为用量统计保存 API 密钥、访问令牌、完整聊天正文、精确位置或邮箱；如需按账号统计，使用受控内部账号 ID，优先展示汇总。
- 不因统计需求改变真实店铺、投稿、评价或账号数据，不默认接入新的第三方埋点平台。

## 分步实施建议

先完成已经记录的注册增长和 AI 用量采集、成功／失败及耗时汇总，再加入地图调用、预算提醒和关键接口健康情况。后续完善搜索到店铺详情／收藏／导航的使用效果、审核效率和资料质量。

实施前逐项确定：指标定义、数据来源、时间范围、管理员能采取的行动以及验收方法。每次只做一小块，不把本记录直接当作一次性全量开发授权。
