# 「城觅」比赛 MVP：现有仓库评估与一周改造建议

评估日期：2026-10-16（澳门时间，UTC+8）。

评估目录：`D:\项目\CityU_Food`；代码基线：`569e09d`。本报告没有假定另一个工作区 `D:\CityU_Food` 与本目录同步。

目标：复用 CTU Food 的现有地图、地点、用户和审核系统，在 2026-10-23 17:00 的 PPT 提交截止前，形成可解释、可演示的「自然语言搜索 → 真实地点 → 多地点路线比较」闭环。PPT 截止时间不等于比赛举办时间，后者尚未提供。

本轮只做分析、只读探测和现有检查；没有修改业务代码、依赖、环境变量或数据库。新增本报告和公开地点路线探测结果。开始检查时已存在未跟踪的 `PLAN.md`，本轮没有改动它。

## 结论先行

**现有代码足以作为比赛 MVP 底座，路线比较也已有实际可行性证据，但当前数据准备严重不足。**

1. 项目已经超出纯餐厅地图：已有生活分类、投稿审核、评论、收藏和权限基础，不需要新建项目。
2. 现有站内导航是高德 URI 外链，没有路线时长查询或多地点比较；AI 调用和自然语言条件提取尚未实现。
3. 使用当前项目的高德 JS Key，在本地生产构建页面实测「城大氹仔校区 → 3 个澳门目的地」，9 次步行/公交/驾车查询全部成功。不能据此声称所有澳门路线、未来时段或后端 REST Key 都已验证。
4. 当前 `.env.local` 连接、匿名访客权限下，`shops` 可见 0 条，`places` 已发布 1 条，且名称带「暂停营业」。用户已说明暂不确定这是不是正式参赛数据库，因此这些数量只代表当前连接与权限下的结果。
5. 一周应交付有限场景、真实数据、可降级的决策辅助 MVP；不能承诺成熟平台、长期偏好学习、实时保证不迟到或全澳门覆盖。

### 1.4 地图、定位、导航

- `components/MapPlaceholder.tsx` 虽叫 Placeholder，实际是高德地图实现，不能按文件名误判成占位组件。
- 加载 `AMap.Scale`、`ToolBar`、`Geolocation`、`MarkerCluster`；支持点击选坐标、地点高亮、视野联动。
- 定位使用 `AMap.Geolocation`，高精度选项、10 秒超时，成功后通过 `onUserLocationChange` 上报坐标；失败显示提示。它依赖浏览器权限和现场网络。本轮没有请求用户真实位置。
- `lib/amap/place-search.ts` 使用 `AMap.PlaceSearch` 分别查询澳门、珠海并合并；POI 候选的距离是 Haversine 直线距离，不能当作路程或行程时间。
- `lib/amap/navigation.ts` 生成 `https://uri.amap.com/navigation`，默认 `mode=walk`。`PlaceNavigationActions` 提供打开导航、复制地址及网页备用链接。
- 没有发现产品代码调用 `AMap.Walking`、`Driving`、`Transfer` 或后端 direction API；本次临时浏览器探测没有把它们写入产品。
- `components/ShopSearch.tsx` 是未发现当前页面引用的旧组件，使用 REST POI 与 GCJ02 → WGS84 转换及 Mapbox 字段命名。新路线实现不要照搬它的坐标转换。先确认地点、定位、POI 与服务接口的坐标体系，并避免重复转换。
- 首页移动端、桌面端各渲染一个地图组件，主要靠 CSS 显示隐藏。新增路线查询应由共享状态或服务触发，避免把同一请求分别绑到两个地图实例。

已核实的可复用查询函数 `public.search_places`：

- 支持 query、分类、标签 UUID、区域、最大价格、最低评分、排序、中心坐标、分页。
- 只查询 published 地点，使用 `security invoker`，保留调用方 RLS 限制。
- 位置计算是近似直线距离，不是路线距离。
- 本轮匿名只读调用成功，返回 1 条地点。
- 当前首页没有调用此 RPC，而是先取旧 `shops` 和 `/api/places` 再在浏览器匹配；`/api/places` 本身只取最多 500 条发布地点，并不是完整搜索 API。
- `openNow` 只存在于 TypeScript 搜索模型/归一化，当前 RPC 和兼容搜索均未实现营业时间过滤。

当前缺少足以执行精确条件的结构化数据：逐日/跨午夜营业时间、临时停业状态、价格来源与核验日期、币种、座位容量、等待时间。MVP 不应补齐一套庞大商户画像；只对实际演示需要的事实进行最小核验。

**当前连接的数据探测：**

- `shops` 匿名可读全部记录：0；`status=verified` 查询也是 0。
- `places` `status=published`：1，名称为「芬记烧腊(新业大厦店)(暂停营业)」，参考价格 60，坐标存在，region 为 null。
- published 记录中没有火锅候选；`hot-pot` 标签本身在当前标签表中存在。
- 因为数据中已有暂停营业字样，published 只能说明内容已发布，不能当作商户正在营业。
- 数量不是管理员权限下的全库盘点，也未证明 Vercel 生产环境连接的是同一个项目。
- `supabase/seed.sql` 明确标为本地 fixtures，含示例店和本地用户，不能导入生产来充当真实商户证据。

### 1.6 用户和权限

`requireUser` 读取 Bearer token 并通过 Supabase `getUser` 验证；`requireAdmin` 再查询 `profiles.role`。前端是否显示管理入口不替代服务端与 RLS 授权。

迁移对新表启用 RLS，区分发布内容、本人投稿/评价、管理员权限；私有 schema 内的管理员判断用于策略及审核 RPC。投稿图片私有、地点图片公开。新 AI 查询应复用匿名/普通用户权限，不需要 service_role。

### 1.7 优先复用的模块与隐患

直接复用地图、Marker、地点卡片、详情、分类标签目录、Zod 校验、`search_places`、API 错误返回和用户校验。新增组件围绕这些接口连接，不重排项目结构。

三个与 MVP 直接有关的历史问题：

1. **新旧表不同步。** 首页同 ID 时优先旧 `shops`；管理员直接新增/编辑写旧表，投稿审批写 `places`。迁移中有一次性 backfill，未发现持续同步链路。AI 只查新表时可能漏掉管理员刚在旧表新增的地点。建议本周演示数据统一进入 `places`，复用投稿审批路径；确有旧记录需要演示时，只做定向、幂等的数据对齐，不重写整个迁移系统。
2. **收藏仍绑定旧表。** 当前脚本中 `favorites.shop_id` 外键指向 `shops`。canonical-only 地点收藏的远程同步可能失败。本次没有验证云端实际外键，不能说故障已复现；先检查，且不把跨设备收藏作为比赛主链路。
3. **品牌未统一。** Header 显示 Lumen Map，页面 title/manifest 是 Macau Pulse，README 是 Macau Student Map，包名为 mu-map。改名需小范围统一 Header、metadata、manifest、README、相关三语言文案和 PWA 版本。

## 3. AI 接入方案

### 3.1 推荐架构

使用一个模型供应商的托管 API，从 Next.js 服务端调用。供应商和模型需要在实际 Vercel 环境测可达性、结构化输出正确率、延迟和成本后确定，不能只凭模型名选择。

不用训练模型，不做通用 Agent，不引入长期记忆架构。现有结构化分类、标签和数据库查询已经适合本任务，现阶段没有引入向量数据库的必要。

```mermaid
flowchart LR
    U[自然语言与确认的出发地] --> P[模型提取条件]
    P --> V[Zod 与标签白名单校验]
    V --> Q[服务端查询 published places]
    Q --> R[代码筛选排序]
    R --> M[地点卡片与地图]
    M --> C[用户选择 2 至 3 家]
    C --> T[真实地图路线结果]
    T --> D[代码比较时长与限制]
    D --> E[AI 根据证据解释]
```

商户事实来自数据库；路程和时间来自地图；预算、人数、活动时长等由用户提供；筛选、加减和排序由代码负责。AI 承担语言理解和结果解释。

### 3.2 自然语言转结构化条件

针对「四个人今晚十点吃火锅，人均 100 以内，离学校近一点」，建议模型只提取这样的意图：

```json
{
  "categorySlug": "food",
  "tagSlugs": ["hot-pot"],
  "partySize": 4,
  "maxPricePerPerson": 100,
  "currency": "MOP",
  "requestedLocalTime": "22:00",
  "originPreference": "campus",
  "priority": "distance"
}
```

这只是设计示例，不是已经实现的 API。日期、UTC+8 时区由服务端结合请求时间归一化；不要让模型自己猜当前日期或“学校”的坐标。选定具体校区与校门，或者使用用户授权的定位。

`hot-pot` 是当前目录的真实 slug，顶层类别仍是 food，不能直接把示例的 hotpot 当成数据库 category。

服务端用 Zod 拒绝未知字段、非法金额/人数/时间，使用本地标签目录把 slug 映射成真实 UUID，再确认数据库标签有效。模型提供合法 JSON 不代表语义正确，仍要校验；例如 DeepSeek 官方 JSON 模式也提示可能返回空内容。[模型输出文档](https://api-docs.deepseek.com/guides/json_mode/)

前端应回显「已识别条件」，让用户能更正预算、类型和起点，并列出「暂无法核实：22:00 营业、4 人座位」。不能把不支持的条件静默丢掉，再声称满足全部需求。

### 3.3 如何查询 Supabase

建议新增 `/api/ai/search`，不改变现有 `/api/places` 列表响应格式。

1. 校验输入长度和会话/访客限额。
2. 模型提取条件，校验后转换成受控 `search_places` 参数。
3. 用普通公共 client 调用现有 RPC，限定 published、分类、标签、价格、区域和坐标。
4. 取小批量候选，例如 10～20 条，展示最多 3 条；有多少返回多少，禁止补造。
5. 按已明确的优先级排序。预算是硬约束，附近是软偏好；价格未知不能当作预算内。没有匹配时明确无结果，可由用户决定放宽条件。
6. 使用返回的地点 ID 重新读取展示事实，通过现有 mapper 转成卡片需要的 Shop。避免把不受约束的原始整句继续作为硬关键词，导致已正确解析的条件再次被关键词过滤掉。

RPC 复用依据：[Supabase 官方 RPC 文档](https://supabase.com/docs/reference/javascript/rpc)。本轮已经验证当前连接能执行此只读函数，但没有修改函数或 schema。

### 3.4 控制幻觉与输出方式

- 模型不能生成 SQL、表名、任意外部 URL 或调用任意工具；只输出白名单意图。
- 查询和事实字段由服务端组装，商户描述/评论视作数据，不能当成系统指令。
- 推荐回复绑定真实 place ID；不接受候选之外的 ID。
- 价格、地址、交通时长由 UI 直接展示结构化事实；AI 文本不作为这些数值的唯一来源。
- 推荐结论先用代码计算，AI 只写简短解释。输出非法、超时或解释与事实不一致时改用固定模板。
- 缺失数据标记 unknown；不要把 null 价格变成免费，或把 unknown 营业状态变成正在营业。
- 第一版不必为每次搜索串行调用两次大模型。先用一次提取 + 规则理由完成闭环；比较阶段再做一次短解释。确需搜索阶段润色时，让卡片先显示、解释后到。
- 不能数学上保证大模型从不幻觉；应保证事实表、候选及排序不由自由文本决定，并有可靠降级。

### 3.5 模型 Key、速度与调用成本

新增服务端变量可采用 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL`；这是建议命名，不是现有已配置字段。Key 不使用 `NEXT_PUBLIC_`，不返回浏览器，不记录到日志。

限制输入长度、候选数量、输出 token、单次超时和重试次数；按会话/IP 限流，并在供应商控制台设置预算上限。可以先把 AI 搜索限于登录用户，现场预先登录，普通地图浏览继续保留。匿名开放时需另有实际的跨实例限流办法，不能认为 Vercel 内存计数器是全局可靠限额。

尚未选定供应商、模型、账号配额与单价，故本报告不编造每次查询费用。估算应为「输入 token × 输入单价 + 输出 token × 输出单价」，再加地图调用费用。建议目标是常规完整交互 5～8 秒内返回、超时进入降级；这是待测验收目标，不是当前性能结论。

### 4.3 结果与排序设计

用户选 2～3 个 place ID → 确认起点及交通方式 → 系统读取真实目的地坐标 → 每目的地、每方式查询 → 统一 `{durationSeconds, distanceMeters, status, queriedAt, source}` → 代码选择该方式返回方案中耗时最短者 → 显示表格和理由。

- 一次是「同一起点到多个独立目的地」，不是 A → B → C 的途经点旅行线路。
- 公交的推荐首方案不必然是最快方案；如果用户问最快，要在返回方案中选择或配置经验证的时间策略，并注明比较范围。
- JS 与 REST 返回字段不同，分别解析；REST v5 获取耗时需要关注 `show_fields=cost`，不能直接套 v3 或 JS 的 `time` 字段。公交还涉及城市编码及日期/时间参数。[高德路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)
- 对外显示分钟前保留秒进行比较，避免整数分钟造成错误并列；距离按路线来源显示，不混用直线距离。
- 使用 `Promise.allSettled` 或等价部分成功策略；限制并发、单请求超时；一路失败返回不可用，不填 0 分钟。
- 比较状态放在共享页面状态，不挂到两个响应式地图实例里分别发请求。
- 首版无需同时画出 9 条路线；表格比较后，仅展示用户选中的目的地/方式路线，降低视觉和性能成本。

### 4.4 是否需要新增后端 API

AI 调用必须走后端。建议的接口边界：

- `/api/ai/search`：自然语言 → 校验 → 真实数据库候选。
- `/api/routes/compare`：采用 REST 路径时负责路线聚合；采用 JS 路径时可暂不创建这一服务端路线接口。
- `/api/ai/compare`：接收候选及问题，读取地点事实，用代码算结论，模型生成解释；模型失败返回模板。

这是拟新增的 API，不是现有文件。可以先完成前两个主流程，再决定是否需要把解释拆成独立接口；不为接口数量而拆分。

### 4.5 Key 安全与限额

当前 JS Key 和 `NEXT_PUBLIC_AMAP_SECURITY_CODE` 会出现在浏览器。JS Key 可公开使用，但需要配置域名限制；安全密钥不能因为名字叫 security 就被视为已保密。官方提供 `serviceHost` 服务端代理配置，可作为有时间时的定向改进。[高德 JS 安全密钥说明](https://lbs.amap.com/api/javascript-api-v2/guide/abc/jscode)

后端 REST 使用单独 Web 服务 Key，例如 `AMAP_WEB_SERVICE_KEY`，不加 `NEXT_PUBLIC_`；不把带 Key 的完整请求 URL写入公开日志。不能把现有 JS 类型 Key 直接搬到 REST API，平台类型和权限不同。

3 家 × 3 方式 = 9 次路线请求；若做往返，是 18 次，不包括 POI、重试和 AI。只需公交时应先查 3 次。采用明确按钮触发、取消旧请求、去重及短期缓存，避免输入每个字或地图每次移动都查路线。缓存/录屏等使用需核对服务条款，展示缓存时间，不能冒充实时。

官方当前基础服务计费表列出认证类型和 QPS，例如个人认证路径规划相关 QPS 为 3；具体生效口径、共享配额和账号剩余额度仍应以控制台为准，本轮没有进入控制台确认，不能保证免费。[基础服务计费说明](https://lbs.amap.com/pages/base_service_price)

高德 2026-10-08 公告称：从 **2026-10-30** 起，香港、澳门、台湾用量及计费与大陆业务独立，并调整相关服务方式。公告晚于项目上次主要代码提交，比赛若在该日之后举办，必须提前复测权限与费用；即便比赛在之前，长期方案也需要重新核算。[官方公告](https://lbs.amap.com/news/yunyingcelue20261008)

## 6. 比赛 Demo 方案

以下是开发完成后的目标流程，当前产品没有 AI 功能。

### Demo A：自然语言搜索（约 45～60 秒）

1. 出发地明确选「城大氹仔校区」或经核验的校门。
2. 输入「四个人想吃火锅，参考人均 100 以内，离学校近一点」。前提是实际整理出符合预算的地点；否则换真实可满足的菜系或预算，不能为话术修改事实。
3. 显示已识别：火锅、人均 ≤100 MOP、4 人、起点。
4. 地图及卡片展示最多 3 个真实结果、参考价和数据缺口。
5. 解释排序依据；4 人只作为需求上下文，不承诺订座或有位。

若增加「今晚十点」，必须显示营业状态核验结果；没有数据时直说未核实，不能声称完整满足。

### Demo B：多地点路线比较（约 60～90 秒）

1. 把 2～3 家加入比较栏，显示固定起点。
2. 询问「现在从学校出发，公交去哪家最快？也比较一下驾车」。
3. 展示每个目的地真实返回的时长、距离、查询时间和来源；分别给出公交与驾车排名。
4. AI 解释不同方式可能有不同首选，地图突出选中的地点。
5. 使用本次探测的不同目的地可展示这种差异，但需要另行核验商户信息及参考价后才能用于正式搜索 Demo。

### Demo C：有限时间内如何选择（可选，约 30～45 秒）

用户说「90 分钟后要回学校，我预计吃饭用 45 分钟」。

由代码计算：`预计返回时间 = 出发时间 + 去程 + 用户指定用餐时长 + 回程 + 用户确认的缓冲`。回程要独立查，不能简单乘二。列出假设，输出「按这些假设较宽裕/较紧张」，不要输出一定赶得上；排队、用餐和临时交通不能保证。只给去程时间时，最多判断到达店铺是否及时，不能判断回到课堂。

五分钟路演建议：40 秒学生困境，40 秒方案与边界，60 秒 Demo A，90 秒 Demo B，40 秒数据/技术与风险，30 秒推进计划。C 只有 P0 稳定才加入，避免挤掉解释项目价值的时间。

答辩表述：不宣称自研大模型；讲清模型解析、数据库事实、路线比较、约束判断和可解释性如何组合。差异化需要以后用真实学生任务完成时间和反馈验证，不能只说“有 AI 所以创新”。

## 7. 风险与 fallback

| 风险 | 证据/影响 | 处理与备用方案 |
| --- | --- | --- |
| 数据量和时效不足 | 当前连接只有 1 条已发布且标注暂停营业；没有预算内火锅样本 | 第一优先确认数据环境和核验真实地点。无匹配明确返回无结果，不用 seed 伪装真实商户 |
| 新旧表分裂 | 首页/管理员/审核/RPC 分别走不同路径 | Demo 统一新 places；定向同步必要旧记录，避免全面重构 |
| 澳门路线覆盖 | 9 个 JS 样本成功，REST 未测，全域全时段未测 | 固定起点和已验证目的地；失败模式显示不可用；JS 是已验证的技术备选路径 |
| 定位失败/人在比赛场馆 | 真实定位可能不在校园；浏览器权限可能拒绝 | 明确选固定校园起点，不伪装当前位置；保留定位入口 |

| 网络与响应慢 | 本轮数据库探测有约 5～7 秒响应及一次失败；不是长期性能统计 | 部署环境测完整交互；分阶段展示、超时、有限重试；准备真实录屏 |
| 地图/AI 配额 | 3×3 为 9 次，往返翻倍；账号配额未知 | 显式按钮触发、按需方式、去重限流、控制台预算；复核 10/30 澳门计费调整 |

| 模型挂了 | 无法理解新句子或生成解释 | 普通筛选继续工作；受支持的明确演示条件可手动选择；路线事实表与规则模板仍能演示 |
| 路线服务挂了 | 无法获取新的真实 ETA | 保留地点/预算比较与外部导航。只有条款允许的已保存真实结果才能带时间戳回放；否则使用录屏，不凭直线距离估时 |
| 演示登录出错 | 邮件登录链路依赖外部服务 | 提前登录，路演不现场等邮件；避免把投稿审核作为主 Demo |

竞争边界：不比商户总量、评论数量和外卖履约；验证「学生带着预算与时间约束，在多个选项之间更快做决定」是否真的有用。推荐若未来商业化，应让商业推广与客观排序来源可辨认；本周不增加商业系统。

## 8. 最终判断与交付边界

**可以争取完成的程度：** 一个使用真实、小规模澳门地点集，能理解有限自然语言条件、显示证据、比较 2～3 个地点真实路线并解释结论的演示 MVP。现有地图和权限体系基本可复用，当前构建与单元测试基线也支持继续小步开发。

**不能直接承诺的程度：** 所有高校/商户覆盖、任意自然语言完全理解、精确营业与座位验证、未来公交实时性、一定不迟到、长期画像、成熟商业模式或大规模稳定服务。

最大的优先级应为：**真实数据 → 数据链路统一 → AI 提取与真实查询 → 多地点路线比较 → 异常降级 → 可选赶课判断**。当前不能把“换名称、接模型”当作已完成产品升级。

三种范围选择：

1. 推荐范围：Demo A + Demo B，保持原地图与卡片，后端路线验证有截止时间，JS 实测路径保底。
2. 更保守范围：若数据整理或每日时间不足，只做可核实条件搜索 + 一种交通方式比较，不做赶课及个性化。
3. 不建议范围：一周内同时完成全澳门多类生活平台、精确营业/座位/排队、长期学习和通用 Agent，明显超出当前基础和剩余时间。

本报告是待确认的评估方案。下一步应先落实 10 月 17 日的「正式数据源、真实候选、模型和路线小样本」，然后按所选范围逐步实施，不开始大规模重构。
