# 收藏、旧店删除与评分一致性

> 2026-10-30 更新：当前数据库旧 shops 已为空，运行时代码已移除旧表读写并统一 places，配套迁移已执行。本文保留此前收藏与删除同步的历史说明，当前状态及发布边界见 [地点数据统一记录](place-data-unification-2026-10-30.md)。代码修改尚未正式部署。

本次修复包含应用代码和两份数据库迁移。迁移必须先在独立测试数据库验证，再按现有数据库发布流程应用；Vercel 构建不会自动执行 Supabase 迁移。不要重新运行旧版收藏建表脚本，也不要重置现有数据库。

迁移顺序：

1. `20261022160000_canonical_favorites.sql`：保留 `favorites.shop_id` 的 API 字段名，将关联目标从 `shops` 改为 `places`。初始迁移中的新旧地点 UUID 相同，已有收藏和创建时间保留；有收藏但尚无新地点副本的旧店会先补齐副本。保留账号自己的读取、插入、删除权限，客户端用忽略重复的插入保证重试安全。
2. `20261022160100_archive_deleted_legacy_places.sql`：删除旧店的同一事务中，将对应新地点副本归档。此前旧店已删除但副本仍可见的记录也会归档；保留地点、评价历史和账号收藏记录。公开查询已有的 `status='published'` 条件会排除归档副本。

应用前后核对收藏总数与最早创建时间，确保未丢失记录。迁移沿用初始回填的新旧 UUID 相同约定，并验证最终外键；若环境中另行改变了 UUID 映射或存在无法映射的记录，迁移会报错，需要先核对数据，不会静默改写或删除收藏。

独立数据库验收：旧收藏仍可读取；登录账号可收藏新发布地点；两个账号不能互读互写；重复收藏可重试；删除旧店后刷新列表和 AI 目录均不再出现，详情和评价接口按未发布处理；事务回滚同时恢复旧店与副本状态。原有列表缓存失效通知继续生效，通知失败时保留原来的 30 秒重验证。

浏览器缓存按游客和账号分别保存。新游客收藏在登录时先转入该账号的待同步记录；离线重试也属于该账号，切换账号不会再次导入。账号缓存只用于读取失败时的本机回退，不会把其他设备已删除的收藏重新上传。

旧共享键 `mz_food_favorites` 无法证明数据属于谁，因此保留原值供排查，但不再显示或自动导入。已有账号收藏会从服务器重新加载。只存在于旧浏览器共享缓存、尚未同步过的记录需在确认归属后单独恢复，不能自动归给当前登录者。

本地回归包含真实 PostgreSQL 兼容的 PGlite 迁移／权限／事务测试及 React 账号切换测试，不需要生产密钥。测试通过不代表迁移已应用到线上。
