# 城觅微信小程序：后续迁移规划

> 整理日期：2026-10-20（澳门时间，UTC+8）  
> 状态：**暂缓实施，仅记录方案**。用户决定先完善现有网站功能，再另行启动小程序开发。  
> 本文是讨论结论与后续路线，不是已完成记录，也不代表已经授权创建小程序工程、注册账号、部署或修改数据库。

## 1. 目标与已确认需求

- 将现有「城觅」扩展为微信小程序，兼顾比赛／作品演示和后续向同学正式开放使用。
- 使用同一套小程序分阶段推进，不另外制作一套与真实业务脱节的演示系统。
- 初期计划使用**个人主体**，后续注册公司，再研究将小程序迁移至公司名下及增加付费内容。
- 本文将用户口述的“个体身份”理解为个人主体，**不是已经注册营业执照的个体工商户**。实施前再次确认。
- 希望提供常见小程序的使用体验：必要的协议说明、微信身份登录、登录状态恢复，以及归属于用户的收藏、投稿等数据。
- 现有网站、数据和网页管理后台继续保留，优先复用已有业务能力，避免大规模重写。

当前优先级：现有网站功能完善与验证在前，小程序迁移在后。本文不设置自动启动日期、开发工期或上线承诺。

## 2. 推荐技术路线及边界

**推荐：新增 Taro + React + TypeScript 小程序客户端，复用现有 Next.js 后端与 Supabase 数据。**

这是当前推荐方向，具体依赖版本、构建配置和接口改造范围，在正式启动时根据届时的代码与官方文档确定。

| 路线 | 判断 |
| --- | --- |
| Taro + React | 优先考虑，延续现有 React、TypeScript 技术栈；页面、样式和平台接口仍需适配 |
| 原生微信小程序 | 可选，使用 WXML、WXSS 等开发界面，需要学习另一套页面组织方式 |
| uni-app + Vue | 可选，目前没有明确需求支持额外切换到 Vue |
| web-view 内嵌现有网站 | 不作为个人主体路线；讨论期间核对的微信官方文档明确说明个人类型小程序暂不支持该组件 |

不能将现有 Next.js 项目直接打包成微信小程序。使用 Taro 或原生开发，也不会自动获得受账号主体、服务类目限制的能力。

## 3. 现有项目的复用与适配

| 部分 | 后续处理方向 |
| --- | --- |
| Supabase 地点、分类、标签和图片资料 | 优先复用，不因新增客户端复制一套正式数据 |
| 纯 TypeScript 搜索、筛选、推荐与校验规则 | 逐项检查平台依赖后复用，避免直接复制整份 lib 目录 |
| Next.js API 与服务端 AI 调用 | 优先保留，补充小程序请求、登录验证与限流适配 |
| 网页管理后台、审核与资料维护 | 继续在现有网站使用，第一版不搬入小程序 |
| React 网页组件、Next.js 路由、网页样式 | 按小程序组件、页面生命周期和布局重新适配 |
| localStorage、浏览器事件、图片压缩 | 替换为小程序可用的存储、生命周期和媒体处理方式 |
| 高德浏览器 JS SDK、定位、POI 与路线比较 | 单独设计适配，验证小程序能力或服务端地图接口，不直接移植浏览器调用 |
| 邮箱登录、收藏与用户数据权限 | 保留内部用户关系，新增微信身份接入与登录会话方案 |

特别注意：当前 AI 模型理解请求在服务端，但地图补充搜索、定位和路线比较仍有浏览器依赖。不能把“服务端 AI 接口可复用”理解成“整个 AI 助手可以直接迁移”。参考 [现有 AI 助手说明](place-assistant-setup.md)。

建议结构（**尚未创建**）：

```text
CityU_Food/
├─ app/                 现有网站、管理后台与 API
├─ components/          现有网页组件
├─ lib/                 现有业务逻辑
├─ supabase/            现有数据库结构和权限
└─ miniapp/             未来新增，独立管理依赖
   └─ src/
      ├─ pages/         发现、详情、AI 助手、我的
      ├─ components/    小程序组件
      ├─ services/      后端请求
      └─ utils/         平台适配与工具
```

小程序优先通过共用后端 API 获取业务数据；图片交付、上传等按实际需要设计。不预先强制把所有媒体流量代理到应用服务器。第一阶段不新增 Python 后端，也不引入复杂的多项目管理体系。

## 4. 微信登录与用户体验

### 4.1 用户看到的流程

1. 首次进入时，按适用规则提供必要的使用说明、用户协议和隐私政策入口，不强制把所有用户操作绑定在一个授权弹窗上。
2. 允许游客浏览地点、搜索和查看详情。
3. 需要云端收藏、投稿或评价时，展示微信登录入口；用户无需另外设置城觅密码。
4. 登录后找到或创建对应的城觅账号，保存该用户的数据。
5. 再次进入时恢复仍然有效的登录状态；凭证失效时刷新或重新登录，不承诺永久登录。
6. 使用定位或选取照片等功能时，再根据实际用途和平台规则处理权限；拒绝定位仍应允许手动选择起点。
7. “我的”提供收藏、投稿、个人资料及退出登录等入口；正式发布前补齐适用的账号与数据管理能力。

协议确认、微信身份登录、手机号获取、头像昵称设置和定位权限是不同事项，不能视为一次点击后全部自动获得。

### 4.2 后端仍然需要做什么

```text
小程序 wx.login 获取临时 code
          ↓
城觅后端调用微信 code2Session 校验
          ↓
取得微信身份，查找或创建对应的城觅用户
          ↓
建立本系统认可的登录会话，返回业务登录凭证
          ↓
收藏、投稿等请求携带凭证，后端继续验证身份和权限
```

- OpenID 不是用户的微信号；身份映射应考虑 AppID 与 OpenID 的组合。
- 不默认一定能取得 UnionID，也不把手机号、头像、昵称作为第一版身份识别的必要条件。
- AppSecret、session_key 与 Supabase 服务端密钥不下发到小程序；OpenID 本身也不能代替登录凭证。
- 现有后端 `lib/auth/require-user.ts` 验证 Supabase 登录凭证，数据库多处通过 `auth.uid()` 和 `auth.users` 外键控制用户数据。
- 因此不能直接把 OpenID 写入现有 user_id，或自行签发一个 token 就假定现有 Supabase Auth／RLS 会认可。
- 启动时需验证微信身份映射、Supabase 用户／会话接入、刷新、退出与权限的完整方案，再决定是否需要数据库迁移。
- 网站邮箱账号与微信身份不会自动合并；后续如需跨端同步，通过验证过的账号绑定流程处理，不能仅凭昵称或头像合并。

## 5. 第一版范围与后续功能

核心闭环：**发现或提出需求 → 查看真实地点 → AI 辅助比较 → 打开地点导航**。

| 功能 | 建议安排 |
| --- | --- |
| 地点列表、详情、分类、搜索、地图 | 基础版本 |
| 定位与手动选择起点、地点导航 | 基础链路打通后验证 |
| AI 对话、地点确认、多地点路线比较 | 核心演示阶段；公开开放前补充费用与请求额度控制 |
| 微信登录、云端收藏 | 账号接入阶段，正式开放使用前验证 |
| 投稿、评价、图片上传 | 核心流程稳定后按需接入；先确认个人主体适用类目与规则 |
| 管理员资料维护、审核 | 沿用网页后台 |
| 付费内容、支付、商业化运营 | 后续公司阶段另行评估，不纳入当前第一版承诺 |

跨设备聊天记录同步、长期偏好学习、复杂消息推送等没有被确定为第一版需求，不因此文自动加入开发范围。

## 6. 分阶段推进与验收

以下阶段仅在用户以后明确要求启动后执行，具体顺序可根据主体权限和技术验证结果调整。

| 阶段 | 主要工作 | 验收重点 |
| --- | --- | --- |
| 0：启动核实 | 重新查看代码、确认主体与服务类目、AppID、域名及发布条件；确定首期范围和账号方案 | 没有依赖不可用权限的主路径，有可执行的小步计划 |
| 1：基础打通 | 建立独立小程序工程，真实地点列表、详情和地图 | 在手机微信中读取真实资料，地点与图片正确，失败有反馈 |
| 2：核心演示 | 搜索筛选、AI 对话、真实路线比较、导航与降级 | 能重复完成核心闭环；缺路线时明确说明，不用 AI 编造时间 |
| 3：账号接入 | 微信登录、会话恢复、云端收藏；按需求扩展投稿评价 | 不同账号不能读取或修改彼此私有数据；登录失效、取消和退出行为正确 |
| 4：正式发布 | 完成适用的主体、类目、备案、隐私与发布准备，补充真机及容量验证 | 关闭调试与跳过域名校验后仍可使用，在目标网络和设备上完成验收 |

已有网站对高德路线的验证不能代替小程序真机验收。澳门／珠海的定位、步行、公交、驾车和跨境路线要分别验证；地图来源、坐标体系及经纬度顺序需明确。

## 7. 上线前待确认事项

- 小程序是否已注册、最终使用何种主体、AppID 与管理员安排。
- 个人主体可选择的服务类目，地点推荐、投稿评论及 AI 助手的实际适用条件。
- 接口与媒体域名、HTTPS、服务器域名和适用备案要求；域名注册完成不等于发布准备完成。
- 当前 Vercel 部署、Supabase 及图片访问链路在澳门和预期用户网络中的实际表现。
- 当前微信登录接入 Supabase 的具体实现与权限方案。
- 后续公司成立后，主体迁移的资格、材料、审核、AppID／用户数据延续及能力调整方式。
- 后续付费内容对应的业务类型、支付资格与平台规则；不能假定主体迁移后自动开通支付。

当前不承诺审核通过时间、固定开发天数或“一天上线”。开发、体验与正式发布的可用范围分别核实。

## 8. 性能与基础设施记录

换成小程序不会自动解决后端性能问题；也不能仅凭“10 人正常、100 人出问题”的转述认定数据库是唯一瓶颈。在线人数、并发请求、数据库连接和 Realtime 连接不是同一个指标。

之前转述资料称 Supabase 在新加坡，但仓库 [2026-10-20 容量评估](capacity-assessment-2026-10-20.md) 记录数据库区域为东京 `ap-northeast-1`、Vercel 函数默认区域为美国东部 `iad1`。本文仅引用该报告，不代表本次重新查询云端配置；启动时应再次核实。

后续依据实际请求与查询数据决定分页、缓存、索引、请求合并、实时订阅和部署区域等调整。不要把本地模拟用户数当成正式网站或未来小程序的容量保证，也不因本文自动升级套餐或迁移服务。

## 9. 以后重新启动时的操作顺序

1. 阅读本文与最新产品待办、容量和发布记录，重新检查 Git 状态及项目结构。
2. 确认现有功能已达到用户希望的完善程度，并取得本次小程序工作的明确范围。
3. 重新核对官方权限与发布要求，确定首期功能和账号接入方案。
4. 更新具体设计与实施计划，先做基础链路验证，再逐步移植功能。
5. 每一步说明修改文件、运行方式、验证结果及剩余问题。

**到本次文档交付为止：不创建 miniapp，不安装依赖，不注册或迁移账号，不改环境配置、数据库和部署，不自动恢复开发。**
