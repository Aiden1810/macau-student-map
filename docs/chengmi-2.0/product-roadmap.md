# 城觅 2.0 长期产品路线图

## 产品定位

城觅从澳门高校美食地图逐步升级为 AI 智能美食决策平台，解决「附近有什么好吃的」「今天吃什么」「怎样根据个人偏好选择餐厅」三个问题。发现地图继续提供真实地点和校园周边生活服务，选餐围绕餐饮场景逐步深化。

## 未来功能

### 1. 智能选餐

- 支持手动筛选和 AI 自然语言选餐。可按人数、预算、距离、菜系、口味、忌口、用餐场景和饮食目标提出需求。
- AI 将需求转换为结构化条件，推荐引擎根据真实商家数据先筛选硬条件，再按偏好排序。价格、路线等资料缺失时显示待确认。
- 支持餐厅比较、换一家、收藏、查看详情和导航。

### 2. 随机决策

- 支持单人转盘和随机抽签。候选项可手动添加，也可按筛选条件从真实餐厅中生成。
- 支持多人提名、投票、否决和随机决策。先支持同一设备多人操作，再评估联网房间和实时投票。

### 3. 饮食记录与口味记忆

- 支持查看最近吃过什么和历史用餐记录，餐后可反馈「喜欢」「一般」「不喜欢」。
- 根据经用户确认的记录和反馈，学习喜欢的餐厅、菜系、口味及饮食习惯。用户可以查看、修改和删除个人偏好。
- 实际用餐必须由用户确认。浏览和导航事件不能自动生成用餐记录。

### 4. 换换口味

- 根据近期用餐记录，降低重复餐厅和菜系的推荐权重。
- 支持换一家、换一种菜系和探索新餐厅。推荐同时参考长期偏好与近期用餐记录。

### 5. 健康饮食推荐

- 支持增肌、高蛋白、减脂、均衡和清淡等目标，以及健身后、食欲不佳、犒劳自己等场景。
- 推荐以真实商家信息及可靠标签为依据。缺少可核实的营养或热量数据时，明确标注资料缺失，禁止由 AI 生成数值。

### 6. 全局 AI 助手

- 规划在全站提供独立悬浮入口。移动端用底部弹出面板，桌面端用侧边窗口。
- 理解当前页面上下文，调用城觅内部数据和业务工具，完成商家搜索、智能选餐、餐厅比较、评价总结、生成转盘候选和饮食偏好分析，并支持多轮对话。
- 按 AI Agent（能够调用工具完成任务的智能助手）建设。用户应能从助手直接进入比较、收藏或导航等业务流程。

## 未来页面结构

| 底部导航 | 功能 |
| --- | --- |
| 发现地图 | 真实商家、学生推荐、搜索、筛选、详情、收藏、导航。 |

## 核心产品闭环

用餐需求 → AI 理解 → 真实商家推荐 → 自主选择、随机决策或多人投票 → 实际用餐 → 餐后反馈 → 口味记忆 → 优化下一次推荐。

## 开发约束

- 正式版城觅是长期维护主线。保留现有可用功能和 Next.js、Supabase、高德地图架构，沿用内部地点 ID 及其收藏、评价、投稿等关联。
- Qoder 比赛版的 `codex/qoder-p0-a`（`920229a`）包含导航和共享助手，`codex/qoder-p0-b`（`8fa5a30`）包含目录选餐、条件表单和随机选餐。已参考其已发布目录筛选和模型提示词候选缩减规则。后续评估独立条件表单、三栏导航和可用测试时，先比对当前 API、路由与页面行为，再决定接入范围。
- 逐步统一商家数据、推荐引擎、用户偏好系统及 AI 工具接口。浏览外部 POI 不自动创建内部商家记录。
- AI 负责理解需求和组织结果。商家、价格、距离、评价及营养数据必须来自可核实的来源，缺失时说明未知。
- 兼顾数据库权限、安全、稳定性、移动端体验、回归测试及 API 成本。尽量节省 Token（模型处理文本的计量单位），同时保留完成开发和验收所需的上下文。
- 未来功能须经用户授权后实施。更新阶段状态时，用实际代码、数据库和测试或发布结果注明验证范围。

### 开源项目利用原则

- 优先核查城觅正式版和 Qoder 比赛版已有的实现、接口和测试，再看上述开源参考。必要时搜索更成熟、贴合现有技术栈的方案。
- 每个新模块开工前，对比现有代码和开源方案，按项目实际情况选择直接复用、局部改造、借鉴设计或自行实现。检查许可证及其适用范围、维护状态、依赖安全、技术兼容性和实际源码质量。复用授权未明确时，仅参考设计。
- 保持 Next.js、Supabase 和高德地图技术体系。按功能需要控制依赖体量，优先复用满足质量、安全和许可证要求的成熟组件，减少重复开发和 Token 消耗。
- 口味记忆初期使用用户主动反馈、用餐历史、标签权重和规则排序。复杂机器学习和向量数据库等到有明确需求、可靠数据和可验证收益时再评估。
- 智能推荐使用真实商家数据，由 AI 理解意图，先执行预算等硬性条件筛选，再按规则排序。
