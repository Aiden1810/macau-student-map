# 城觅容量评估：2026-10-20

本轮完成套餐核实、正式接口的少量只读基线检查，以及本地隔离容量测试。**本地模拟用户数不是正式网站的用户容量承诺。** 本轮不部署、不升级套餐、不执行远端迁移，不在正式库写入地点、评价或统计，也不批量调用付费 AI、地图与邮件服务。

官方当前默认限额中，Supabase Free 的 Realtime 并发连接为 **200**，消息为 **100 次/秒**，每秒 channel joins 为 **100**。实际项目限制可配置，本轮未读取项目 Realtime 自定义设置，因此这里是套餐默认值。首页目前会给打开页面的浏览器建立实时订阅；不同标签页与后台也可能消耗连接。超限首先影响实时订阅，不等于整个网站无法提供静态或普通查询服务。[Supabase Realtime 限额](https://supabase.com/docs/guides/realtime/limits)

Free 的普通出站流量包含 5 GB、数据库大小包含 500 MB；这些是套餐额度，**不是当前剩余额度**。没有获取月内实际流量用量，也没有把月活登录额度当作并发容量。[Supabase 套餐](https://supabase.com/pricing)

Vercel 官方建议让函数靠近数据源。当前美国东部函数与东京数据库的组合值得优先检查；本轮没有迁移区域，不能声称已验证区域变更的性能收益。[Vercel 函数区域](https://vercel.com/docs/functions/configuring-functions/region)

## 3. 测试如何隔离

目录与职责：

```text
scripts/capacity/
  run.mjs       复制应用、构建生产版本、分档施压和保存报告
  fixture.mjs   隔离 PostgreSQL、虚构资料和有限 HTTP 数据适配器
  metrics.mjs   P50/P95/P99、失败率、吞吐量和目标地址检查
tests/capacity/
  metrics.test.ts
  fixture-cleanup.test.ts
```

- 从 Git 已跟踪及未忽略文件中，只复制产品源码和必要配置，跳过所有 `.env`、`.vercel`、文档和测试。副本位于 Git 忽略的 `output/capacity/<时间>/app`，不覆盖原应用构建。
- 副本使用实际 Next.js 生产构建与当前实际 `/api/places`、`/api/places/:id`、`/api/search/events`、`/api/places/:id/reviews` 路由。
- Next 子进程的 Supabase URL 和 public key 显式替换为本机测试地址和假 key，DeepSeek key 清空。没有复制、输出或覆盖原 `.env.local`。
- 测试数据库为已有开发依赖 PGlite。复用仓库实际表结构、评价迁移、评价权限和评分事务；以虚构用户和 50／500 个合成地点运行，没有图片。
- 有限的 PostgREST/Auth 适配器只提供本次受测路径；Auth 是虚构账号映射，普通列表和搜索记录 SQL 以测试数据库 owner 执行；评价 RPC 在真实 PostgreSQL authenticated 角色与 `auth.uid()` 下执行。
- 压测目标硬编码为 `127.0.0.1:56547`，数据适配器为 `127.0.0.1:56548`。目标检查拒绝公网、携带凭据的 URL 和跳转，启动前校验本次随机 fixture 标识与合成地点内容。
- 端口冲突时不结束占用端口的其他进程。fixture 初始化失败会清理自身数据库和定时器，并有子进程退出回归测试。
- 原有 56544／56545 预览保留；压测完成后关闭自身的 56547／56548 服务。

没有安装新依赖，也没有修改产品行为。前一轮平台管理员后台的未提交工作保留。

## 4. 场景与验收口径

**浏览场景：** 两组资料量分别测试 10、25、50、100 个虚拟用户。每档 15 秒，每位用户反复执行“读取列表 → 读取一个详情 → 写入一条隔离搜索记录”，每轮之间停顿 1 秒，启动在 500 ms 内错开。每轮都重读列表，属于较频繁重新打开页面的 API 场景；前端真实搜索主要在浏览器内完成。

**评价场景：** 10、25、50、100 个不同虚构账号，各同时向同一个隔离地点提交一条 4 星评价，测试真实评价事务的突发请求。它不是持续写入吞吐量测试，也不代表真实 Supabase Auth 的能力。

**本地验收阈值：** 请求失败率为 0；列表成功响应 P95 ≤ 2000 ms，详情和搜索记录 P95 ≤ 1000 ms。这些是本次选定的初始目标，不是平台保证或行业统一标准。

- 除 HTTP 状态外，还校验业务结果：列表条数与虚构名称、详情 ID、搜索是否真正 recorded、评价评分与地点 ID。200 但内容不正确仍计为失败。
- 超时为 10 秒，超时和语义失败均进入失败率分母。报告分别保留成功响应与所有响应的 P95。
- 分位数使用 nearest-rank 方法。没有样本时显示 null，不将空样本视为零延迟。
- RPS 是已完成请求数除以实际测量时间，包含排空在途请求所用时间。并发突发评价的 RPS 是单次突发的平均值，不当作可持续吞吐量。
- 命令退出 0 表示采集执行完成，不代表所有档位达标；浏览档位查看 `results.json` 的 `passed` 字段；评价突发查看 `summary.failures`、失败率与延迟，没有独立 `passed` 字段。

## 5. 实测结果

最终完整复测证据：`output/capacity/2026-10-20T02-53-33-175Z-full/results.json`，同目录附副本源码 SHA-256 清单和生产构建日志。环境为 Windows、Node 24.14.1、AMD Ryzen 9 7945HX、32 个逻辑 CPU，物理内存约 15.2 GiB。测试机不等同于免费云数据库规格。

评价调用实际保存 RPC、评分聚合与账户限频逻辑，但数据库是本机单进程 PGlite，不能据此承诺云端每秒持续写入几百条。

**对当前上线决策的结论：** 本地小目录的应用 API 路径通过了 100 虚拟用户测试；目录扩展到 500 条后，100 用户档位不满足本次延迟要求。正式接口的低负载响应约 1 秒且函数跨区域访问数据库，真实免费云环境尚未完成多用户全流程验证。应先以“50 人同时正常浏览”为后续云端验收目标，不能写成“当前已保证线上支持 50／100 人”。

## 6. 上线容量仍未覆盖的部分

1. 本机 CPU、内存与 PGlite 的单进程执行方式不同于 Vercel 和正式 Postgres；load generator 也运行在本机。内存读数是测试驱动与隔离数据库进程的合计 RSS，不是正式数据库内存需求。
2. 数据适配器不是正式 PostgREST；列表查询不是其自动生成的原始 SQL，也没有重现全部正式 RLS 和数据库连接竞争。
3. 未包含页面 SSR、JS/CSS、图片、浏览器渲染、地图、WebSocket 实时连接、真实登录和邮件。API 测试的虚拟用户不能等同于真实全功能同时在线用户。
4. 未验证付费 AI 或高德账号的实际余额、自定义配额和峰值吞吐，没有发起付费模型压力请求。AI 使用量不能从浏览测试推算。
5. 测试是短时 closed-loop（用户等本轮响应后再发起下一轮），负载增加后吞吐量可能下降；没有测到独立到达率负载、长时间稳定性、故障恢复或推广瞬时突发。
6. 正式评价迁移与新搜索读取迁移仍未执行；隔离测试中的新评价成功不代表线上评价已经启用。

因此，本轮能回答“当前应用在这台机器、这组流程和样本下的表现”，不能宣称正式网站支持 100／1000 人同时使用，也不能承诺固定 DAU。

## 7. 后续顺序

1. 先在本地设计并验证公开地点列表的短时共享缓存，以及发布／编辑／评分变动后的刷新规则。
2. 核对页面实时订阅的必要性：目前首页订阅的是旧 `shops` 表，新地点来自 `places`；不要为了低频资料变化让每个访客都保持无必要的连接。
3. 评估将 Vercel 函数放到更靠近东京数据库的地区；需另行获得发布授权并做前后对照。
4. 为 AI 增加跨实例生效的账号限流、全局预算与降级策略；当前内存按 IP 每分钟 8 次，不能视作全站预算保护，也可能影响校园共用出口的同学。
5. 在接近正式配置的独立环境做云端全流程测试，再确定可承诺的人数和扩大推广的节奏。需要云环境、可能产生费用或发布动作时，先将具体方案与费用交给用户确认。
